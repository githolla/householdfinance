# CLAUDE.md

Read this before touching anything. Keep it current — if you change the architecture, change this file in the same commit.

## What this is

A shared-finances app for a couple: budget, spending, bills, goals, net worth, reports, and an AI planner panel that answers with the household's own numbers. It was prototyped as a single Claude artifact and lifted into Vite. Everything works today; nothing is mocked except the data source.

## Stack

Vite + React 18 (JSX, not TS yet) · recharts · plain CSS in a template literal · localStorage via a shim · xlsx (SheetJS) and mammoth extract spreadsheet/Word text client-side in the Files view.
No Tailwind, no component library, no router. Don't add any without being asked.

```
npm install
cp .env.example .env      # add ANTHROPIC_API_KEY for the planner panel
npm run dev               # localhost:5173
```

## File map

```
src/App.jsx      the entire app — ~1,900 lines, default export
src/main.jsx     mounts App, imports the storage shim first
src/storage.js   window.storage backed by localStorage (see contract in the file)
src/scripture.js verse list (World English Bible, public domain) + deterministic daily pick
vite.config.js   dev proxy that attaches the Anthropic key server-side
api/anthropic/v1/messages.js  the same proxy as a Vercel serverless function (needs ANTHROPIC_API_KEY env var in Vercel)
docs/            data model + roadmap
```

`App.jsx` is organised in labelled sections, top to bottom: helpers → demo-data generator → CSS → `App` (shell, nav, persistence) → `model()` → shared components (including `Concierge`, the AI omnibar mounted atop Overview, Budget, and Spending with per-page suggestion chips — one sentence logs spending, sets up a bill or income, runs `find …` local search, or falls through to a planner-brain answer shown inline and appended to the Assistant chat; local regex fallback when the AI route is unreachable; pasting a multi-line "Name — $Amount" list opens a bulk review. `buildSnapshot`/`buildPlannerSystem`/`searchEverything` are the shared brain between the omnibar and `PlannerPage`) → ten view components → `Setup`. `PlanAhead` (the "Plan ahead" view) is the what-if builder: upcoming big items live in `state.scenarios` (`{name, amount, date, fund: "save"|"cash", items:[{name,amount}], days}`). A trip can be broken down to the penny via `items` (a "trip template" seeds Flights/Hotel/Food/…); when items exist the total is their sum, and `days` gives a per-night figure. Each line item (`TripItem`) has a built-in estimator (`calcSpec` picks gas/food/lodging/flights/rental/generic from the item name) that computes an amount from a few inputs and drops it in. The **Calendar** view (`CalendarView`) lays the month out as a grid — bills due, income expected, spending logged, and planned items on their days, colour-coded, with a hover tooltip and click-through day-detail panel, today highlighted. **Trip tracking**: entries carry an optional `tripId` linking them to a Plan-ahead scenario; the Spending view shows a trip tracker card (budget vs. spent-tagged-across-months vs. left, with "Add trip expense" and a "show only this trip" filter), the add-transaction modal and `EntryRow` editor both offer a trip selector, and tagged rows show a ✈ trip chip. Each scenario shows a precise read — total, per-night, the monthly set-aside, and the exact headroom/shortfall against what free cash flow (save) or cash on hand (pay from savings) can cover by the date — plus the before→after on free cash flow and runway, a rough 12-month cash projection (as-you-are vs. with-the-plan), and a one-tap "Make it a savings pot". Reuses `m.monthlyNet`/`m.cashTotal`/`m.monthlyCost`/`m.runwayMonths`; scenarios flow into the planner snapshot as `upcomingPlans`. `FilesSection` — the household's searchable paper drawer — renders inside the Bills view (`state.docs`, capped at 100k chars per doc): uploads are extracted to text on-device — SheetJS for spreadsheets/CSV, mammoth for .docx, plain read for everything else — and each doc can be sent to the AI for a stored "planner's read" (`doc.analysis`).

## The one thing that matters architecturally

**`model(state, plan, month)` is the whole computation layer.** Every derived number in the app — totals, per-envelope spend, goal projections, debt payoff simulation, planner notes, the headline sentence, the fair-split read — is computed there and passed down as `m`. View components render; they don't calculate.

Keep it that way. If you need a new number, add it to `model()` and read it off `m`. Do not compute totals inside a view.

## State shape

Single object, persisted as one JSON blob under `twocolumn:v2`, debounced 450ms. See `docs/data-model.md`.

Two rules that will bite you:
- **Months are lazy.** `state.months[month]` may not exist. The `plan` memo falls back to cloning last month's envelopes with fresh ids. It only gets written when the user edits. Always mutate months through `writeMonth()`, never `patch()` directly.
- **Envelope ids are per-month.** The same envelope in March and April has different ids. Cross-month matching is by `name` (see "Match last month's actuals"). Any feature that reasons across months has to account for this.

`patch(fn)` deep-clones state, applies `fn`, sets. Fine at this data size; revisit if a household ever has thousands of transactions.

## Conventions

- Money is stored as plain numbers, formatted at the edge with `money()`. Never format for storage.
- Month keys are `"YYYY-MM"` strings. Use `shiftMonth`, `monthsBetween`, `monthLabel` — never do date math inline.
- `owner` is `"a" | "b" | "joint"` everywhere (envelopes, entries, bills, accounts). Resolve with `m.ownerName()` / `m.ownerColor()`.
- All user input goes through `num()`, which strips currency formatting and never returns NaN.
- Colours live in the `C` object and the CSS variables. The theme is bright, warm, and modern — a clean personal-finance dashboard: warm off-white ground `#F5F1EA`, **white** cards `#FFFFFF` with 1px `#ECE7DD` borders and a soft low shadow (`--shadow`), rounded `--r:16px`, ink `#1B2420`. The **sidebar is dark** (`--sidebg #18211E`, light nav text, teal active pill with a left accent, rounded right edge); the month-nav is a pill. Accent is teal `--a #0F6B60` (focus rings/links/active use ink or teal). Deep teal `#0F6B60` is partner A, burnt amber `#B0670A` partner B, indigo `#3D4A8F` shared/goals, `#C0392B` the only alarm, `#3F8A3B` the good green (income, giving, "up"). `Kpi` takes a `dark` prop for hero stats (ink card, white text). `GROUP_COLORS` runs the spending families — teals for essentials (Home/Daily/Health), ambers for discretionary (Lifestyle/Other), green for Giving — and paints the donut + allocation rail (segments clustered by group, `%` labels, red-striped unassigned tail).
- Type: Instrument Sans (body), Bricolage Grotesque 800 (h1–h3/`.serif`, tight `-.02em`), IBM Plex Mono for every figure (`.num`, KPI values). Buttons `.btn` are mono uppercase 11px on ink; `.btn.ghost` is the light variant (and sidebar-scoped for the dark ground). Loaded via `@import` in the CSS string.
- The shell is a dark left sidebar on desktop (grouped nav with inline SVG icons from `IC`, an unpaid-bills badge, household avatar, balance + build tag + start-clean + Daily bread in the footer) and a fixed bottom icon bar on mobile (≤900px). **Nav is split simple/advanced** via `NAV_SECTIONS` (`[label, items, advanced?]`): the core "Money" section (Overview, Budget, Spending, Bills & files, Pots, Dreams, Assistant) is always shown; the advanced "More tools" section (Calendar, Insights, Plan ahead, Net worth, Reports — `ADVANCED_VIEWS`) is collapsed behind a `.navtoggle` and hidden unless `state.showAdvanced` is on (absent = off) **or** the current `view` is itself an advanced one (`advOpen`), so deep-links from core pages still resolve and reveal the section. `SETTINGS_NAV` sits on its own at the foot; the mobile `bottomNav` follows the same visibility. The **Simple / Full** switch lives in Settings ("How much to show"). Every advanced view still renders when routed to via `setView`; it's only hidden from the nav. Above every view sits a `TopBar` (greeting + partner names, a "Search & ask" button → Assistant, a one-tap **Upload** button, and partner avatars). Upload opens `UploadModal` — a global drop/pick that extracts files on-device via `extractText` and files them to `state.docs`, reachable from anywhere.
- **Insights** (the "Insights" view, `Insights`) is the intelligence hub: the `HealthCard`, spending **patterns** ("what moved this month" — each group vs. its trailing 3-month average, as diverging bars; plus "where it's going" top merchants/notes), the six-month income-vs-spending trend, and **debt-payoff scenarios** (avalanche vs. snowball, an extra-per-month input, debt-free date / interest / months-saved, and an at-minimums-vs-with-extra balance chart from `m.payoff(extra, strategy).series`). Framed with a debt/diligence verse. Add new pattern logic here, reading `state.months`. The Overview is **at-a-glance**: a 4-KPI row (current balance [dark] · income · spent · available), a compact `Concierge` bar, the `HealthCard`, then cards — a spending **donut** (`Where it went`), **recent transactions**, **pots** progress, **recurring-bill status** tiles, **coming up** (plan-ahead scenarios), a compact **giving** card, and the six-month cash-flow chart + planner notes. Setup keeps a paper-gradient `.hero` band.
- **Transactions** (Spending view) paginate at `PER_PAGE` (10) via the shared `Pager` (prev/next + numbered), with search (note + category), a sort select (latest/oldest/A–Z/high/low), and who/category filters; page resets when the result set changes. **Budgets** (`EnvRow`) expand via a chevron to show that category's latest 3 transactions. **Pots** (the Goals view, `PotCard`) show progress and a keyboard-friendly add/withdraw control that moves money in/out of `saved` with inline validation. **Bills** have search + sort. Forms show inline `.fielderr` validation messages when required fields are missing.
- **The balanced-budget guideline (`m.framework`)** is a biblical 50/30/20 — the tithe first. Envelope groups roll into four buckets (Give = Giving; Needs = Home/Daily/Health; Wants = Lifestyle/Other; Save = goals), each with a target % of income: give = `faith.givingTarget` (10), needs/wants/save from `state.framework` (default 50/20/20). `FrameworkCard` on the Budget page shows each bucket's actual share vs. its target (bar + marker) with a plain read; the targets are editable in Settings (Give is set by the tithe target). Snapshot carries `budgetGuideline`. Change bucket→group mapping via `BUCKET_OF` in `model()`.
- **The income-needed read (`m.incomeNeeded`)** is computed in `model()`, built up from the bills so it comes alive the moment bills are entered. Three non-overlapping tiers — `bills` (the floor), `run` (+ everyday envelope spend that isn't a bill or the tithe), `full` (+ giving and savings; equals `allocated + billsOutsidePlan`, so `gap` matches `monthlyNet`) — plus the component parts (`bills`/`everyday`/`giving`/`savings`), `income`, `gap` (+ to spare / − short), and `coversBills`/`coversRun`/`coversFull`. `IncomeNeededCard` renders it at the top of the Bills view: a stacked bar of the four parts with a marker for take-home income, a plain read, and the three tiers ticked green when income clears them. Snapshot carries `incomeToCoverTheMonth`. It reuses the same figures as the health read; don't recompute — extend `incomeNeeded` in `model()`.
- **The financial-health read (`m.health`)** is computed in `model()` and is the household's overall standing once income + bills (+ accounts) are entered. It scores five vitals a planner watches — monthly cash flow, fixed-bill ratio, savings rate, debt load, emergency runway (cash ÷ monthly cost) — each 0–100 with a `good`/`watch`/`serious` status, and takes their weighted average as `m.health.score` (0–100) with a `label` (Getting started → Strained → Watchful → Steady → Thriving), a one-line `read`, and `actions` (the weakest non-good vitals as concrete steps). `HealthCard` renders the SVG gauge, the vitals grid (each tile drills to the relevant view), and the actions; the snapshot passes `financialHealth` to the planner. Status colours: `--good` green / `--b` amber / `--warn` red via `STATUS_C`. Add a new vital in `model()`, not the view.
- **Dreams + the investing sandbox** (the "Dreams" view, `DreamsView`, in the core nav) is the long-horizon layer. `state.dreams` (`{id, name, target, saved, targetYear, invest, returnPct, owner}`) holds big life goals; `model()` computes `m.dreams` for each — `saveMonthly` (plain) vs `investMonthly` (solved at `returnPct` via `solveMonthly`), `fundMonthly`, `pct`, `affordable`/`shortfallMonthly` against `m.freeCash` (= `max(0, monthlyNet)`), `investSaves`, `reachYear` — plus `m.dreamsTotal/dreamsSaved/dreamsMonthly` and `m.invest`/`m.invested` (sum of `invest`-type accounts). `DreamCard` shows the plain read and a save-vs-invest toggle (writes `d.invest`). The add-dream modal offers presets (`DREAM_PRESETS`, Mission trip first; the Debt-free target auto-fills from `m.debtTotal`) **and** an auto-enter field: `guessDream(name, m)` turns any typed name into a sensible target/horizon/mode by keyword (debt/emergency targets read off the real numbers). `InvestSandbox` is a **play-money** what-if: a starting amount, a monthly, a horizon, and a risk mix (`RISK_MIXES` → assumed %/yr, editable) run through the compound helpers (`fvGrow`, `solveMonthly`, `monthsToTarget`, module-level, above `model()`), charted against cash. `DreamsView` is **tabbed** (`My dreams` / `Investing sandbox` / `Learn to invest`) so it isn't one long scroll; the KPI row + dream cards live on the first tab, the sandbox and guide on their own. `InvestGuide` is the **learn-to-invest** layer: a readiness ladder computed from the household's real numbers (cash cushion via `runwayMonths` → high-cost debt via the top-APR debt account → tax-smart accounts via `invested` → investing toward a dream) plus a **two-level accordion** (`LESSONS` → each with an intro and clickable `subs`): how investing works · safe practices · what you can invest in · a biblical view (WEB verses, gated on `m.faithOn`), each sub-topic expandable for a detailed plain-language read — general education, not product advice. Every figure is an illustrative estimate on a fixed assumed return — never advice, never a real transaction; the copy and the planner snapshot (`dreams`, `investedToday`, `freeCashFlowForDreams`) say so. Add new dream/investing logic in `model()` or the helpers, not the view.
- Every hero/KPI card drills into more: `Kpi` takes `onClick`/`active` and clickable ones get a corner `→` (or `↓` when they toggle something open — a filter, an expansion). Destinations are the place you'd act on the number: cross-view via `ctx.setView`, on-page via `scrollCard(id)`, or a local filter (Spending's paid-by, Bills' unpaid-only, Goals' behind-only). The Overview hero card itself is a button into Budget. Keep new KPI cards clickable — a dead-end summary card is a bug in this design.
- No `<form>` elements — click handlers and Enter keydowns only. Carried over from the artifact; harmless to keep.

## The stewardship layer

Optional biblical layer, on by default, toggled off via `state.faith.enabled` (absent = on; read it through `m.faithOn`, never directly). What it is:

- **Daily study**: a short daily Bible study on money and wisdom lives in `src/scripture.js` (`STUDIES` + `studyForDay`, deterministic by calendar day) — each has a passage (WEB), a two-line reflection, a "talk about it" question for the couple, and a one-line prayer. The Overview leads with a green **Today's study** banner (`.studybanner`) and the sidebar Daily bread card both open the `DailyStudy` modal (opened via `ctx.openStudy`, gated on `m.faithOn`). It's **context-aware**: `studyContext(m, month)` reads the day — overdue bills → a debt study, income landing today → provision (with a first-fruits nudge), giving goal not yet met → giving, bills due soon → planning, tithe met/bills clear → contentment — and returns both the theme (fed to `studyForDay(theme)`, studies tagged via `STUDY_THEME` in scripture.js) and a live "For your day" line tying the study to their real numbers, shown on the banner and atop the modal. Add studies to `STUDIES` (+ a `STUDY_THEME` entry); keep them WEB and finance/wisdom themed.
- **Guidance banners front and center**: every view opens with a `Guidance` banner under its page head — a verse themed to that view (planning on Budget, contentment on Spending, debt on Bills, diligence on Goals, provision on Net worth, together on Reports/Settings, giving on Planner) plus one line tying it to the live numbers. The Overview banner and the sidebar's compact Daily bread card use the day's main verse, deterministic by calendar date (`verseForDay` in `src/scripture.js`) so both partners see the same verse. `model()` picks the verse's *theme* from the shape of the month — over plan → contentment, over-planned → planning, heavy debt ratio → debt, no giving set aside → giving — otherwise it rotates. The `verseLine` under it ties the verse to their real numbers.
- **Giving numbers** (`m.giving`) come from envelopes in the existing `Giving` group — that group is the hook; don't invent a parallel structure. The Overview's Giving card measures the month against `state.faith.givingTarget` (% of income, default 10, set in Settings) and shows year-to-date; `m.giving` carries `target/targetPct/ytd/lastMonth/metTarget`.
- **Milestones** (`m.celebrations`): a debt account reaching zero, the giving target met, or giving beating last month surface a celebration card on the Overview — plain warm copy, real numbers, a fitting verse; "Mark the moment" stores it in `state.milestones`/`milestoneLog` (shown in the Giving card, fed to the planner). Celebrations are the one sanctioned warmth — still no confetti, badges, or streaks.
- **Planner/Assistant** gets today's verse + giving stats in the snapshot and may frame advice as stewardship when it fits; its prompt forbids preaching, guilt, and using scripture to settle a disagreement. The Assistant view (`PlannerPage`) is also the app's chat-upload-search surface: files dropped into the chat are extracted, filed to `state.docs`, and read aloud in-conversation; "find …" messages run an instant local search across docs, bills, entries, goals, and incomes; mic input and a read-replies-aloud toggle round it out.

Verses are WEB (public domain). Add verses to `scripture.js` with a theme tag; never quote copyrighted translations (NIV, ESV, etc.). The voice rule below applies doubly here: the app observes, it never sermonises.

## Voice

The app talks like a planner who knows them, not a dashboard: one plain sentence about the state of the month, specific numbers, no exclamation marks, no gamification, no "You've got this!". The headline sentence and planner notes are generated in `model()` — match that register when you add copy.

## Known gaps (in rough priority order)

1. **Single-browser storage.** Both partners can't use it. This is the big one — see `docs/roadmap.md`.
2. **Manual transaction entry.** No bank feed.
3. **AI on other hosts.** `api/anthropic/v1/messages.js` covers Vercel (set `ANTHROPIC_API_KEY` in project env vars); the app path `/api/anthropic/v1/messages` is served by the Vite proxy in dev. Any other host needs its own equivalent route. The route is public — keep the model allowlist and token cap in it.
4. **No tests.** No test runner installed.
5. `App.jsx` is one file. Split it when it starts hurting, not before — and split by view, keeping `model()` and the shared components together.
6. Net worth is a live snapshot, not a tracked series. There's no history to chart yet.

## Non-goals

Specific investment advice (which fund/stock to buy), real brokerage/trading, tax logic, credit scores, multi-currency, more than two partners. The investing sandbox is deliberately **play money** — illustrative compound-growth projections on an assumed return the user sets, for planning what a dream takes; it never recommends products, never moves real money, and always says so. Keep it that way: no live quotes, no "buy this", no guarantees.
